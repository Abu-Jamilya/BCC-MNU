# BCC MNU · Агент проверки требований

Агент проверяет спецификацию до начала разработки. На входе — PDF, Markdown или TXT. На выходе — отчёт на русском языке с цитатами, расположением дефектов и выводом о готовности к разработке и тестированию.

Проект для [BCC-HUB × MNU FinTech Hackathon](https://github.com/BCC-HUB/ai-requirements-validator-task).

## Запуск

1. Установите [Node.js 22 или новее](https://nodejs.org/). Для PDF на Linux или Windows также нужен `pdftotext` из Poppler в `PATH`. В macOS агент может использовать встроенный PDFKit. Для Markdown и TXT достаточно Node.js, пакетов npm нет.
2. Из корня репозитория выполните `cp .env.example .env` (в PowerShell — `Copy-Item .env.example .env`). Получите ключ в [Google AI Studio](https://aistudio.google.com/apikey) и заполните `GEMINI_API_KEY` в `.env`. По умолчанию агент обращается к `gemini-3.5-flash-lite`. Параметр `GEMINI_MODEL` можно изменить.
3. [Скачайте документ организаторов](https://raw.githubusercontent.com/BCC-HUB/ai-requirements-validator-task/main/docs/requirements.md) и сохраните его, например, в `inputs/requirements.md`. Выполните следующую команду.

```bash
node validator.mjs --input inputs/requirements.md --output output/report.md
```

Для PDF замените значение `--input` на путь к выданному `.pdf`. Агент создаст папку для отчёта при необходимости. Если файл отчёта уже существует, он будет заменён после успешного прогона.

Для OpenAI укажите `LLM_PROVIDER=openai` и `OPENAI_API_KEY` в `.env`. Ключ можно создать в [OpenAI API Platform](https://platform.openai.com/api-keys). Модель по умолчанию — `gpt-4.1-mini`. Её можно переопределить через `OPENAI_MODEL`. Значения из окружения имеют приоритет над `.env`. В Git достаточно хранить `.env.example` с пустыми ключами.

### Локальная модель через Ollama

Установите [Ollama](https://ollama.com/) и запустите его. Выполните `ollama pull qwen3:4b`, затем укажите `LLM_PROVIDER=ollama` в `.env`. Для локального режима ключ не нужен. Агент подключается к Ollama на `127.0.0.1:11434`. Можно указать другую совместимую модель с поддержкой структурированного JSON через `OLLAMA_MODEL`. При запуске через Ollama также учитывайте размер контекста модели и производительность компьютера. На CPU-раннере GitHub полный учебный прогон достиг лимита времени. Для прогона в Actions используйте Gemini или OpenAI.

### Прогон в GitHub Actions

Владелец репозитория сохраняет ключ `GEMINI_API_KEY` или `OPENAI_API_KEY` в Settings → Secrets and variables → Actions и выбирает провайдера в [Generate submission report](https://github.com/Abu-Jamilya/BCC-MNU/actions/workflows/submission-report.yml). Workflow скачивает зафиксированную версию документа организаторов, сверяет SHA-256 и запускает ту же команду, что приведена выше.

На странице успешного прогона в разделе **Artifacts** доступны два архива.

| Архив | Содержимое |
| --- | --- |
| `BCC-MNU-submission-report` | Оригинал `inputs/requirements.md` и автоматически созданный `output/report.md`. |
| `BCC-MNU-demo` | Видео `demo.mp4` на русском. В нём показаны команда, этапы из журнала, цитаты и уточняющий вопрос из отчёта, проверка для QA и итог прогона. При отсутствии замечаний видео показывает сводку без разбора дефекта. |

Для видео workflow устанавливает FFmpeg, Pillow и шрифты DejaVu. В обычном CI сборка видео проверяется на коротком примере с имитацией API. Такое видео помечено «Тестовый пример» на каждом кадре.

## Что проверяет агент

| Этап | Результат |
| --- | --- |
| Каталог | Краткие формулировки и ссылки на исходные строки. Явные ID сохраняются, остальные пункты получают ID агента и исходные цитаты. |
| Проверка отдельных пунктов | Замечания к однозначности, полноте, проверяемости, атомарности, необходимости, уместности, осуществимости, корректности и соответствию формату. |
| Проверка спецификации целиком | Сопоставление разделов, интерфейсов, бизнес-правил и критериев приёмки. Поиск противоречий, пробелов и несогласованной терминологии. |

Рубрика основана на свойствах требований и их совокупностей из ISO/IEC/IEEE 29148:2018 (§5.2.5–5.2.6) и IEEE Std 830-1998 (§4.3), указанных в задании. Агент выполняет статическое ревью текста.

Node.js проверяет JSON модели и полноту индивидуального ревью. Ссылки проверяются по индексу документа, а цитаты подставляются из исходного текста. Для противоречия на уровне набора нужны две разные ссылки. В отчёте сохраняются время UTC, SHA-256 документа, провайдер, модель и Git-коммит (тег релиза при запуске из архива).

В начале отчёта собраны до трёх вопросов владельцу продукта. Они отсортированы по серьёзности, при равном приоритете первыми идут вопросы по набору требований. По ссылке на ID можно перейти к месту в отчёте, прочитать исходные цитаты и увидеть, как QA сможет проверить согласованное решение.

## Проверка и ограничения

```bash
node --test
```

Тесты используют имитацию ответов API и проверяют разбор документа, ссылки, полноту ревью и запись отчёта. Результат живого прогона зависит от модели и исходного документа. Для PDF нужен текстовый слой. Если скан состоит из изображений, сначала выполните OCR. Для PDF со смешанным содержимым отчёт отмечает страницы, из которых текст не извлечён. Лимит входа — 100 000 символов извлечённого текста.

При выборе облачного провайдера в его API уходит извлечённый текст. Для прогона используйте документ организаторов или материалы, которые разрешено передавать выбранному провайдеру.
